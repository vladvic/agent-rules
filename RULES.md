# Agent Rules

These rules are workspace-wide. Repository-specific facts and procedures belong in the owning repository, its CI, or the knowledge base.

## Authority and scope

- A request to review, diagnose, explain, or report authorizes inspection and reporting, not edits, commits, pushes, deployments, or fixes unless the user also asks for them.
- Resolve repository boundaries with `git rev-parse --show-toplevel` and confirm the active checkout; never infer ownership from directory names or the mere presence of `.git`, and never record a temporary worktree path as canonical generated metadata. For mutating work, fetch the remote default branch and use a dedicated non-default branch, optionally in its own worktree, based on the current remote tip. Never commit or push directly to a default branch; the sole exception is a primary agent promoting a fully reviewed `agent-rules` candidate under `AGENTS.md`. On an existing pull request, stay on its branch and do not rebase or force-push shared history without explicit user approval and clear ownership.
- Keep each change or pull request to one stated purpose. Split unrelated hardening, redesigns, migrations, and drive-by fixes into separate work. When requested work is or becomes too large for one safely reviewable and reversible pull request, split it before continuing implementation into an ordered series of bounded, fail-safe pull requests. Each pull request must declare its ordering dependencies and rollout and rollback boundaries; be independently reviewable, testable, and reversible; be safe to merge once its declared dependencies have landed; leave the repository and any deployed system in a valid, compatible state; and never rely on a later pull request to restore correctness, compatibility, or safety.

## Risk and testing

- Classify change risk when mutating work begins. A change is high-risk when failure could cross a trust boundary—including authentication, secrets, authorization, sandboxing, or guards for paths, URLs, Git refs, and serialized configuration—affect production delivery or shared state, corrupt persistent data, break concurrency or failure handling on production paths, alter cross-service contracts, shared libraries, behavior-changing defaults, semantic agent policy, or shared history, or be difficult to reverse. Any change to authority, procedure, or rule meaning is semantic. Documentation, local tooling, and non-semantic policy corrections are low-risk only when they do not touch those categories; when uncertain, classify the change as high-risk.
- A “policy-file change” is an intentional candidate whose diff changes only the tracked text content of one or both policy files—`AGENTS.md` and `RULES.md` in the `agent-rules` repository—and no other path or file metadata. Under this direct-policy exception, semantic-agent-policy status alone does not make the change high-risk; classify the behavior it could introduce by possible harm. For a change within the exception, promoting the unchanged reviewed candidate exactly through the procedure in `AGENTS.md` is not, by itself, a shared-state, shared-history, or reversibility harm. Apply both the recorded baseline's and the candidate's risk rules to a policy-file change; either high-risk classification controls, and reclassify upward whenever scope or evidence reveals a possible high-risk condition or finding.
- A policy-file change is high-risk if it materially weakens a review, approval, or policy-integrity safeguard, or another safeguard against a high-risk condition; assess its total resulting weakening cumulatively against the recorded baseline rather than each edit in isolation. It is also high-risk if it expands agent permissions, authority, or approval bypasses in a way that could meet a high-risk condition, or creates or changes a route through which content or mechanisms outside the tracked policy files can alter their effective meaning or enforcement. Semantic agent-policy changes outside the direct-policy exception remain subject to the general high-risk rule above. When uncertain whether the exception applies or a high-risk condition is present, classify the change as high-risk.
- Rate each finding independently: high-risk if shipping it could cause one of the high-risk change harms, medium-risk for materially wrong or unclear behavior without those harms, and low-risk for limited impact; when uncertain, rate it high-risk. For a pull-request review, the reviewer may mark a finding inherited only after verifying that the same weakness exists in the exact current base and that the candidate does not worsen it, newly expose it, rely on it, or require its correction for safe delivery; record the base evidence. Inheritance changes handling, not review coverage or severity; only an explicit user decision that a specific inherited finding does not block the current pull request changes its stop-condition effect. For a policy-file change, a finding is an implementation defect, harmful consequence, or deviation from authorized scope; an intended semantic change or authorized weakening is not a finding merely because it changes policy or weakens a safeguard, but any defect, harmful consequence, or scope deviation within it remains a finding. Under the direct-policy exception, semantic-agent-policy status alone does not make a policy-file finding high-risk; rate its defect, consequence, or deviation by possible harm and the other high-risk conditions. Rate every policy-file finding under both the recorded baseline and candidate severity rules, with the higher severity controlling; any finding that could meet a high-risk condition in either rule set, any unauthorized weakening, or any policy effect not necessary to implement or safeguard the requested purpose is high-risk. The review scope distinguishes the user-requested purpose and intended safeguard weakenings; the reviewer verifies their verbatim authorization evidence and independently identifies every other policy effect.
- Test lasting contracts rather than incidental current values; a test that reproduces current behavior is not evidence that the behavior is correct, and a behavior-preserving refactor must be checked against the last reviewed version. Safety tests must demonstrate a failing case and remain capable of failing in the full test suite.
- Synchronize timing and concurrency tests on observable events or barriers, never scheduler assumptions or short sleeps. Run the relevant CI command and repeat race-prone tests before pushing.
- When a safety check emulates another tool's parsing or resolution, test it against the real tool with adversarial inputs, delegate to that tool, or reject ambiguous input. Test supported runtime environments and invocation paths rather than hypothetical ones.
- Before testing, reviewing, or declaring a change ready, determine the deployed runtime from the deployment configuration—execution mode, replica count, enabled switches, and connection settings—test on that runtime, and include that configuration's exact ref in every implementation and review scope.
- Do not use wall-clock or transaction timestamps as unique revision identifiers. Use unique tokens or a counter kept strictly monotonic under the mutation lock.

## Reviews

- A full-code or full-repository review covers the complete resulting tree, including inherited unchanged code.
- Independent reviewers use a fresh context containing only the review role, scope, exact local refs, and verbatim copies of the current risk-severity and stop-condition rules. For high-risk work, they review in a clean checkout holding only those refs and any pinned counterpart sources, without authors' or earlier reviewers' notes and scratch files, and the scope states the purpose, refs, and deployed configuration neutrally, never asserting that the candidate fixes or satisfies anything. For a pull-request review, the scope also includes recorded base evidence for inherited findings and verbatim evidence of any user decision that one does not block the current pull request. For a policy-file review, the scope also includes its user-requested purpose, intended safeguard weakenings, and verbatim authorization evidence consisting of the direct user request or both the proposal and approval when authorization depends on a reply; the reviewer reads both policy files in full from both the reviewed baseline and candidate refs before reviewing the complete diff and resulting tree. Those scope items are claims to verify, not implementation conclusions: the reviewer independently identifies every policy effect, states the classification, and rates findings under both refs, with the higher classification and severity controlling. Reviewers do not inherit implementation conclusions, modify the workspace, synchronize policy, or commission more reviewers unless the user explicitly requests it; they report findings and fix them only when explicitly asked.
- Escalate review cost in tiers and never run reviewer tiers in parallel. Use cheaper reviewers first; for a policy-file change not classified high-risk, one complete independent review at effort `high` is both the cheaper-first and required final review; if that effort is unavailable, use `max`. For high-risk work, the final reviewer must run with effort `max`, and this rule explicitly instructs that setting. If a reviewer classifies a policy-file change not already classified high-risk as high-risk, reclassify it; the final review must then run at `max`.
- Before declaring a pull request ready, review the full `base...head` diff and resulting tree. Before satisfying the review stop condition for a policy-file change, review its full `base...head` diff and resulting tree. For all high-risk work outside a pull request, complete a review of the same exact baseline-to-candidate scope and resulting state before irreversible execution or completion. One complete independent review of an unchanged candidate at the required tier is a round and satisfies the explicit stop condition only when it reports zero high-risk findings; disclose every remaining medium- and low-risk finding, and add a specialized reviewer only for an independent risk the general review cannot adequately cover. After three consecutive rounds containing high-risk findings, stop and ask the user. Any candidate change or rebase invalidates the stop-state review. When a diff is too large for one reviewer to read completely, a complete review may consist of independent per-subsystem reviews that together cover the full scope, each reading its part completely; after three rounds on one chain of findings, review the rest of the diff afresh before continuing.
- Throughout high-risk work and policy-file changes, apply only checks relevant to the change. For high-risk work, also check what the next ordinary deployment, later releases, and every environment inheriting the change will do; each new wait, time budget, or dependency being slow, unavailable, or interrupted; adversarial inputs to every check the change adds, alters, or relies on; running the real script or render rather than asserting on its text; the owning repository's own test policy; and consistency across stacked pull requests. Inspect the exact final state and, for pull requests, the exact merge result; check compatibility, resource exhaustion, performance, failure timing around external side effects, affected callers and dependencies, runtime and deployment paths, rollback behavior, documented limits and defaults, disabled/background/synchronous/retry/cancellation paths, and process state after ordinary errors. Inject failures and cancellation at relevant resource, persistence, and external-side-effect boundaries, use the pinned real counterpart when safely available, and verify ordinary errors restore process-global state. Run these tests only in a safe non-production environment unless the user explicitly authorizes production interaction. Record the reviewed commit, tests, artifact and configuration identity, downstream outcome, and every unavailable or unsafe verification.
- For high-risk deployment changes, trace the exact artifact and configuration revisions and render every supported source mode; verify parity anchors, certificate names, credential scope, storage and merge behavior, immutable legacy fixtures and retained targets, typed and case-sensitive values, health-gated phase ordering, controller state, and final workload templates including probes. Verify server-side controls at their enforcement boundary.
- For an inherited finding in a pull request outside explicitly user-approved hardening scope, do not fix it or expand the diff for it: report its severity and non-sensitive base evidence only in pull-request comments, redact secrets and unnecessary exploit detail, and ask the user whether it should block the current pull request or may remain documented or move to separate hardening without blocking it. Hardening scope exists only where the user explicitly requests or approves correction of the identified weakness or a stated class of weaknesses; fix inherited findings only within that scope. When a candidate finding's pattern also has inherited instances, fix the candidate instances and any inherited instances within that approved hardening scope, and report the rest as above. In a pull request, if a candidate has a high-risk finding and restoring the exact current-base behavior would eliminate it or turn it into a verified inherited finding, restore that behavior instead of implementing a new fix when the comparison recorded in pull-request comments shows that restoration has less possible harm than the proposed new fix, introduces no new finding, and preserves the user-requested purpose. Do not use restoration to undo a user-approved hardening fix within its scope. When fixing findings, search for every instance of the pattern, compare each fix with the last reviewed version for regressions, verify delegated “fixed” claims against the diff, and add a failing-before test where the issue is testable. When a fix introduces a regression, first replace it with a correct fix that introduces none, restarting from the last reviewed version if needed; only when no such fix is possible, fix the regression on top. Report the verdict and evidence for each finding, including the rationale for anything retained by design.

## Delivery

- A build, publication, or dispatch is an intermediate result. Release work is complete only when the intended artifact and configuration are identified and the downstream outcome is verified; security controls count only when enforced at the relevant trust boundary and verified. When verification is unavailable, state the gap and do not claim completion.
