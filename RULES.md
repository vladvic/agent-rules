# Agent Rules

- Every primary, delegated, or spawned agent must read this file in full once when it starts a new session or run in this workspace.
- Do not reread this file for every prompt or task within the same session or run.
- If this file changes after an agent last read it, the agent must reread the updated file before continuing work.
- After reading this file, follow `AGENTS.md`, including its knowledge-base usage and maintenance instructions.

## Good Practices

- For high-risk pull requests, validate the exact generated merge commit and require at least one fresh-context, whole-diff adversarial review before declaring no actionable findings. A code review must inspect every changed file plus affected callers, dependencies, runtime paths, and deployment paths; it must resolve all actionable issues found within scope rather than stopping after the supplied findings are fixed. Reviewers must expand beyond prior findings and green tests to inspect dependency boundaries, rollout and backward compatibility, failure timing around external side effects, concurrency and resource exhaustion, and performance regressions; tests that merely codify current behavior are not evidence that the behavior is acceptable. Trace release and deployment workflows through generated commits and cross-repository handoffs, verifying the deployed artifact identity and the downstream outcome rather than treating build or dispatch acceptance as completion.
- For timing, concurrency, and background-worker changes, make tests synchronize on observable events instead of assuming scheduler order or relying on very short wall-clock windows. Synchronize concurrency tests on observable lock attempts or explicit barriers before asserting exclusion; a fixed sleep is not evidence that a contender reached the protected operation. Before pushing, run the exact CI command and runtime where practical and repeat the affected timing-sensitive tests enough to expose nondeterminism; one passing suite is not sufficient evidence that a race-prone test is stable.
- When the user requests a whole-code or whole-repository review, inspect the complete resulting tree, including unchanged code inherited from the base branch; do not restrict findings or fixes to the feature-branch diff.
- When asking Claude to review code changes, start a fresh Claude session and provide only the review scope plus the repository/ref needed to inspect the changes; do not resume a prior implementation or discussion session or preload its context.
- Escalate review cost in tiers: cheap reviewers first (Codex, Claude at low effort); fix and re-review at that tier while it keeps finding anything; invoke the max-effort reviewer only once the cheap tier is clean and Codex reports no high- or medium-risk findings. Do not run the max-effort reviewer in parallel with cheap reviewers, and stop it as soon as they report findings.
- Before new cross-repository work, fetch `origin/main` in every in-scope repository and create a dedicated feature branch from each current remote-main tip; never reuse an unrelated PR branch or work directly on `main`. When fixing an existing PR, stay on its branch, fetch remote main, and rebase it before further work only when it is behind.

## Bad Practices

- Do not infer project or repository scope from directory names, layout, or the mere presence of `.git`; verify repository boundaries with `git rev-parse --show-toplevel` and confirm the workspace's active ownership before describing or acting on repository scope. In this workspace, the maintained vault gateway is `llm-core/vault-gateway`, part of `llm-core`; do not treat the legacy top-level `vault-gateway/` checkout as a separate project.
- Do not treat wall-clock or transaction timestamps as unique revision identifiers. For stale-write checks, use a unique revision token or enforce a strictly increasing value under the mutation lock, retaining its high-water mark after revisions are cleared.
- Honor shared-runtime hosting constraints. Do not require a runtime per user when a restricted shared service is intended; assess server-enforced capability allowlists and isolation of user state, credentials, and sessions instead.
- When adding GitOps services or chart source modes, run the existing render/parity suites as well as new tests. Compare baseline parity only for anchors present in the baseline; separately render every current-only anchor through all applicable charts. Verify rendered certificate common names match the issuer's SAN requirements. For staged rollouts, validate both foundation and enabled-process renders, including Kubernetes annotation types, DNS/certificate sync order, pull credentials for each registry host, and the repository-required apply/retention options on persistent volumes.
- Do not turn one-time PR non-regression observations into permanent CI assertions that freeze unrelated services' replica counts or rollout strategies; test lasting contracts instead.
- Audit image and protocol compatibility in every declared deployment environment. Match runtime configuration parsing or reject noncanonical values explicitly.
- Validate staged activation with the actual downstream deployment verifier, including the final serialized values and base/environment merge order.
- Preserve the canonical repository root in tracked generated metadata; never commit a temporary worktree path as the authoritative root.
- Validate release changes across artifact publication, configuration promotion, and runtime reconciliation, including direct-main write paths and retained workflow revisions. Protect write credentials with server-side ref restrictions, not only checks in new workflow source; distinguish a prepared credential migration from verified external enforcement. Break bootstrap dependencies explicitly and gate cross-service phases on observed health; per-Deployment strategies do not order independent GitOps Applications. For staging-only changes, compare live pod templates against the baseline, including probe settings.
- Keep legacy-image negative tests on immutable fixtures, and run the full available CI workflow against a complete activated candidate. Require established deployment targets explicitly when controller retention means removing their declarations does not retire them. Match case-sensitive runtime policy enums exactly.
- When fixing review findings, do not fix only the cited line: search for every instance of the same pattern. Do not relay a delegate's "fixed" verdicts unverified: check each against the diff and a failing-before test, then report a per-finding table (verdict, commit, evidence), including items kept by design with code evidence.
- Do not clear a PR on delta-only review rounds. Before calling it ready, run one fresh full-scope review of `base..head` with repository access, not excerpts chosen by the author. Have reviewers check integration code against the counterpart's pinned source (how it parses our errors, responses and types). Check that every timeout, limit and default promised in docs, comments and flag descriptions matches the code. Test on the production driver and invocation paths, plus off-paths: flag off, background/cron runs, sync invocation, cancellation mid-call. After a decision changes behavior, re-review code that relied on the old behavior. "No critical/high findings" is not a reason to stop before that full pass.
- Do not review fixes only for whether they close their finding. In each fix round, compare every fix commit's behavior with the last approved version and list new failure modes. Inject faults at every point a change adds (new connection, lock, slot, time budget, "persist then act" step): the step fails, or a cancellation lands exactly there. Test integrations against the real counterpart with a proxy, latency, gzip and at least three concurrent calls, not only fakes. Finish with two independent final reviews with different briefs: regression and fault injection, and a fresh full read. Do not let one finding chain run more than about three rounds before the rest of the diff gets a fresh look. Treat "behavior-preserving" refactors as claims to verify with the same regression lens.
- Do not test a safety check that emulates another tool's parsing or resolution (paths, YAML, Git refs, URLs) only against your own expectations. Test it against the real tool with adversarial inputs (symlinks with `..`, merge keys/anchors/duplicate keys, branch-and-tag names, alternative URL spellings), or ask the tool itself or refuse ambiguous constructs. Do not rely only on a sanitized CI environment: also cover macOS (or mark the code Linux-only), real user Git/Helm config, tokens set, and offline runs. For process-global state, test continued use after an ordinary error, and confirm safety tests can still fail in the full test session. Check exit codes and signals against how callers (shell loops, CI) react.
- Keep a service deployment PR limited to its manifests, minimum shared deployment support, and directly required backend rollout integration. Move unrelated runtime hardening, release-system redesigns, credential migrations and general bug fixes to separate work; assess backend dependencies individually rather than dropping or including them wholesale.
